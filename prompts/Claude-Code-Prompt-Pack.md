# حزمة برومبتات Claude Code لتنفيذ تطبيق نايل بترو (Flutter)

## لماذا تفشل البرومبتات المنسوخة من ChatGPT
1. مكتوبة بلا رؤية للمستودع، فيخمّن النموذج المسارات والأسماء.
2. تطلب كل شيء دفعة واحدة، فيضيع ما هو دقيق.
3. بلا معيار «انتهى» قابل للاختبار.
4. بلا مرجع بصري، فيرسم النموذج واجهة من عنده.

الحل: سياق ثابت (CLAUDE.md)، ثم شريحة عمودية واحدة لكل برومبت، ثم اختبار يثبت النتيجة، ثم مراجعة قبل الشريحة التالية.

## قواعد الاستخدام (لكم أنتم)
- افتح المشروع في VS Code وشغّل Claude Code من جذر المستودع.
- برومبت واحد لكل جلسة. لا تدمج الشرائح.
- ابدأ كل برومبت بوضع التخطيط (Plan Mode) واطلب الخطة قبل الكتابة.
- ضع لقطات التصميم (PNG) في `design/screens/` ليقرأها Claude بنفسه.
- بعد كل شريحة: `git commit`، ثم جلسة جديدة.
- لا تقبل «تم» دون مخرجات الاختبار.

## 1) إضافة إلى CLAUDE.md (يُلصق مرة واحدة في جذر المستودع)

```
# نايل بترو — قواعد ثابتة للتنفيذ
## المصدر
- الحزمة المجمّدة RC02.5-FC للقراءة فقط. أي تغيير تصميمي يمر عبر NP-CR-xxx.
- التغييرات المقبولة من NP-CR-002 تُطبَّق فقط بعد قبول المالك.
## المعمارية
- Single-Tenant White-Label، نواة SaaS-ready. لا مبدّل مستأجرين.
- الخادم هو المرجع. recordVersion رمز معتم، لا حساب عليه.
- closeWorkerShift متصل فقط ولا يدخل الطابور.
## قرارات المالك (2026-10-06)
- قراءة العداد: كاميرا حية فقط، لا معرض أبداً.
- العامل يرى اللترات فقط أثناء الوردية، ويرى المبلغ عند إنهاء الوردية فقط.
- المدير يرى مبيعات (لتر ومبلغ) ومصروفات وفرقاً ومخزوناً، ولا يرى الربح ولا سعر الشراء إلا بمنح المالك.
## الواجهة
- ألوان وأحجام وأنصاف أقطار من tokens فقط. أي HEX داخل شاشة = عيب.
- RTL أولاً. أرقام لاتينية معزولة اتجاهياً (2 / 4 لا تنقلب).
- أهداف اللمس ≥48. نص ≥12 ولا نص ظاهر لاسم برمجي.
- كل نص للمستخدم من مفاتيح الترجمة (ICU).
## العمل
- لا تضف مكتبة دون ذكر السبب في الخطة.
- كل ميزة بجانب اختبار. لا تُنهِ دون تشغيل: flutter analyze && flutter test.
- لا تغيّر ملفات خارج نطاق الشريحة. لو احتجت، توقف واسأل.
- عند أي غموض في عقد، سجّله في PENDING-QUESTIONS.md ولا تخترع قيمة.
```

## 2) برومبت الشريحة S1: الغلاف والثيم والدخول

```
اقرأ أولاً بالترتيب: CLAUDE.md، 04-Contracts/flutter-implementation.md،
04-Contracts/architecture.md، 04-Contracts/authentication.md،
ثم M0-STATUS.md وملفات tokens المولّدة.

الهدف: هيكل تطبيق Flutter للعامل والمدير يقرأ الإعدادات والثيم من مزوّد واحد،
مع شاشات البداية والدخول (رمز العامل + رمز الدخول الشخصي + البصمة المقيّدة بالسياسة).

الخطوات:
1) ادخل Plan Mode وأعطني خطة بأسماء الملفات والحزم قبل أي كتابة.
2) أنشئ طبقات: config provider (loading/loaded/failed)، theme من tokens، router (go_router)،
   مخزن آمن، عميل شبكة، قاعدة محلية مشفرة.
3) نفّذ شاشات: splash، login، enrolment offer، biometric login، وفق لقطات design/screens/.

لا تفعل: لا تضف شاشات غير مذكورة. لا لون ثابت. لا بديل ثيم مخفي عند فشل التحميل.

معيار الانتهاء:
- flutter analyze بلا تحذيرات.
- اختبار ثيم: كل ألوان الشاشات من tokens (فحص آلي).
- اختبارات Golden للشاشات الأربع بتكبير نص 1.0 و1.3 و2.0.
- مقطع قصير أو لقطات من محاكي بحجم 390x844 وبحجم أصغر 360x640.
اعرض لي الناتج: الملفات المضافة، نتيجة الاختبارات، وما تأجّل ولماذا.
```

## 3) برومبت S2: وردية العامل (القلب)

```
اقرأ: CLAUDE.md، 04-Contracts/offline-sync.md كاملاً، business-rules.md، permissions.md،
وصور design/screens/worker/ (البداية، القراءات، النهاية، المراجعة).
إن وُجدت صور NP-CR-002 المقبولة في design/screens/after/ فهي المرجع للشاشات W1..W4.

الهدف: بدء وردية، قراءات بداية لكل مسدس، قراءات نهاية، مراجعة، إنهاء متصل فقط.

متطلبات:
- طابور دون اتصال بمفتاح idempotencyKey لكل نية، وإعادة محاولة أسية (1ث، ×2، حد 60ث، 8 محاولات).
- الحالات الخمس للسجل ومركز المزامنة (شريط ثابت + شاشة حالة).
- recordVersion رمز معتم. عند 409: ألغِ المحاولات، احفظ مسودة استرداد، واعرض صنف التعارض كما يعلنه الخادم.
- قراءة العداد: كاميرا حية فقط (بلا معرض)، وإدخال يدوي كبديل دائم.
- المبلغ يظهر للعامل في شاشة ملخص الإنهاء فقط (W5)، وبعد إدخاله النقد المعدود. لا تعرف آلي في هذه الشريحة إلا إن كان NP-CR-002 مقبولاً.
- حفظ القراءة لا يعرض شاشة نجاح كاملة (إشعار سفلي ثم المسدس التالي) إن اعتُمد NP-CR-002.

ابدأ بخطة ثم نفّذ على مراحل: (أ) نموذج البيانات والطابور مع اختباراتها، (ب) الشاشات.
معيار الانتهاء:
- اختبارات وحدة للطابور: قطع الشبكة في كل خطوة، إعادة تشغيل التطبيق وسط العملية، تكرار الإرسال.
- اختبار تكامل: وردية كاملة دون اتصال ثم مزامنة.
- Golden لكل شاشة، وفحص عدم ظهور أي نص برمجي.
- تقرير بالحالات التي لم تُغطَّ.
```

## 4) برومبت التعرف الآلي على العداد (بعد قبول NP-CR-002 وتجربة الصور)

```
الهدف: اقتراح قراءة العداد من الكاميرا على الجهاز دون إنترنت.
اقرأ: PENDING-QUESTIONS.md (Q-04) وعقد صورة العداد.
المتطلبات:
- كاميرا حية فقط. لا اختيار من المعرض (قرار المالك).
- التعرف يقترح فقط. العامل يؤكد أو يعدّل، والخادم هو المرجع.
- أرقام لاتينية فقط، وتجاهل أي حرف غير رقم، وتحقق من 3 خانات عشرية.
- إن انخفضت الثقة، افتح الإدخال اليدوي دون عرقلة.
- سجّل في كل قراءة: هل جاءت من الاقتراح أو يدوية وهل عُدّلت (للتحليل لا للعقوبة).
قبل الكتابة: اقترح خطة تجربة على 30 صورة حقيقية من عدادات مضخاتنا وحدد حد القبول.
```

## 5) برومبت S3: المدير (لوحة، موافقات، إغلاق المحطة)

```

وصور design/screens/manager/ و after/M1 وM2 إن اعتُمدت.
الهدف: لوحة المدير، الموافقات (قراءة، مصروف، توريد)، جاهزية وإغلاق وردية المحطة.
قواعد صارمة: المدير لا يرى أرباحاً ولا سعر شراء ما لم يمنحه المالك. الإرجاع يتطلب سبباً.
الإغلاق متصل فقط. اعتماد وإرجاع بقرار نهائي لا يُعاد تطبيقه (DECISION_CONFLICT).
معيار الانتهاء: اختبارات صلاحيات لكل شاشة بدور المدير، وGolden، وفحص لا أسماء برمجية.
```
